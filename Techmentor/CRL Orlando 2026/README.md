# DefXDRLabKit — Azure Red/Blue Defender XDR Lab

A guided PowerShell framework that builds, configures, demos, and tears down the
Red/Blue **Microsoft Defender XDR** lab in Azure — driven entirely from your
Windows machine. Built for presenting live: every step **narrates what it is
doing and echoes the actual command on screen** before it runs it, so your
workshop audience follows along and you never have to remember or re-type a
command.

> Authorized educational / detection-training use only, in a lab subscription
> you own. Techniques are generated by **cited public runners** (Atomic Red
> Team) invoked by ATT&CK ID — there is no exploit code in this package.

---

## Walkthrough: build the range from your PC (start here)

This is the order to run the kit on a Windows machine, from a clean start to a
range you can demo. Work top to bottom; each step lists what you should see.
The kit is a work in progress, so the menu labels below match the current build.

### Prerequisites

Install these on the Windows box that will run the kit. Menu 9 (or the startup
check) prints a pass/fail table and the exact fix command for each miss. Menu 9
then offers to **install the missing ones for you** — command-line tools via
`winget`, PowerShell modules via `Install-Module` — so you can go from a clean
Windows box to ready in one step.

| Requirement | Why | How to get it |
|-------------|-----|---------------|
| **PowerShell 7+** (`pwsh`) | The kit is PowerShell 7 code; Windows PowerShell 5.1 will not run it | `winget install --id Microsoft.PowerShell`, then open `pwsh` |
| **Azure CLI** (`az`), 64-bit | Every deploy and in-guest step runs through `az` | `winget install --id Microsoft.AzureCLI` (64-bit MSI at aka.ms/installazurecliwindows). A 32-bit build works but prints OpenSSL warnings |
| **An Azure subscription you own**, with Contributor rights | The lab creates a resource group, VNet, six VMs and NSG; it bills while running | Use a lab subscription. Never a customer or production subscription |
| **The `guest\` folder beside the script** | The numbered guest scripts (03 to 11) are pushed into the VMs from here | Keep `DefXDRLabKit.ps1` and `guest\` in the same folder, and let OneDrive finish syncing before you run |
| **Defender for Endpoint Plan 2** on the tenant | WIN11 onboards to MDE and the ASR and CFA steps need it | Tenant licensing, not a kit setting |
| **Defender for Identity license** (optional, for the DC sensor) | Needed for MDI sensor activation on DC01 | Tenant licensing. DC01 must run Windows Server 2019 or later with the September 2026 cumulative update |
| **PowerShell module `Microsoft.Graph.Authentication`** | Only for Graph-based advanced hunting (Blue / hunting-pack menus); everything else runs without it | `Install-Module Microsoft.Graph.Authentication -Scope CurrentUser`, or let menu 9 install it |
| **Internet access from your PC** | The kit detects your public IP to lock the NSG to you, and reaches the Azure and Defender portals | Normal home or office connection |

Optional: Git, if you want to clone this repo rather than download it.

### Step 0: Launch and sign in

1. Open `pwsh` in the lab-scripts folder and run `./DefXDRLabKit.ps1`.
2. The startup check runs. Fix any red row before going on.
3. The Azure context gate runs. Choose **L** if you need to sign in or switch.
   Pick the **lab** subscription by number, then type its name exactly to confirm.
   **Stop here if the name is not your lab subscription.** The kit will not deploy
   to a subscription you did not confirm.

### Step 1: Check your configuration

Menu **1 → 7** saves the lab settings to `%USERPROFILE%\.defxdrlab\config.json`.
Check these values: resource group `rg-defxdr-lab`, location (for example
`canadacentral`), domain `lab.local`, NetBIOS `LAB`, and whether to include SRV01.
Leave auto-shutdown **off** while you build (menu **1 → 6**), so a build is not stopped halfway through.

### Step 2: Build the infrastructure

Menu **1 → 1 (Deploy the Azure range)**. This creates the resource group, VNet `192.168.57.0/24`,
the NSG (inbound locked to your public IP only), and the VMs: DC01, WIN11, WIN11B,
and KALI. Expect roughly 15 to 25 minutes. Each command is echoed before it runs.

Check: menu **1 → 4 (Status)** shows the VMs running.

### Step 3: Configure the domain

1. Menu **2 → 1 (Configure DC01)**. DC01 becomes the `lab.local` domain
   controller, its DNS points at itself with an Azure DNS forwarder, and the lab users
   are seeded. The DC restarts as part of the promote.
2. Menu **2 → 2 (Join targets)**. WIN11 and WIN11B each point their DNS at
   the DC first, with Azure DNS as the secondary, then join the domain and restart.

Check: menu **2 → 3 (Verify lab readiness)** reports both victims joined and resolving
`lab.local`. If a join fails, run menu 2 → 1 again first, because the join
depends on the DC.

Both steps are safe to re-run.

**Lab passwords.** The admin accounts (the DC's DSRM password and the
`labadmin-da` Domain Admin) get a **random password per lab**, generated the first
time you run menu 2 → 1 and saved in `%USERPROFILE%\.defxdrlab\secrets-<copy>.json`,
outside the repo. Menu **2 → P** copies them to the clipboard or rotates them. The
seeded attack-target accounts keep their **deliberately weak** passwords, because
cracking and spraying them is the lesson.

### Step 4: Blue-team setup and hunting

Onboarding is automatic: Defender for Cloud and the build-time push install
Defender for Endpoint on every Windows VM, and the MDI v3.x sensor activates on
DC01 by itself. Menu 4 is now mostly about **hunting**.

1. Menu **4 → S** checks that every lab device is in Defender and its sensor is
   healthy. If one is missing, **4 → E** pushes the MDE.Windows extension now.
2. Menu **4 → G** (one time): installs the small `Microsoft.Graph.Authentication`
   module for your user and signs you in with `ThreatHunting.Read.All`, so the kit
   can run advanced hunting directly. An admin may need to consent once.
3. Menu **4 → H**: pick one of 12 course hunts (directory recon, one account on
   many hosts, Kerberos, LSASS access, ASR, AV detections, alerts, run command,
   app credentials) and see the results in the console. **4 → A** shows the
   last day's alerts by product. Queries that read Sentinel tables (run command,
   app credentials) need the workspace from menu **6 → 1**. If a hunt cannot run
   from the kit, the query is copied to your clipboard and Advanced hunting opens.
4. **4 → 3** turns on Controlled Folder Access and network protection; **4 → 4**
   verifies. The Defender Baseline GPO (menu **2 → 9**) is optional.
5. **4 → M** holds the manual fallbacks (local onboarding script, classic MDI
   sensor, MDI gMSA), for when automatic onboarding did not happen.

Check: WIN11 appears in security.microsoft.com within a few minutes. DC01 appears
under Defender for Identity once the sensor reports.

### Step 5: Demo and verify

- **Menu 2 → 7** builds the Hardened Systems OU and baseline GPO. Use **2 → 8** to
  move a box into it, reboot, and re-run the attack to show what the baseline closes.
- **Menu 5** runs one technique by ID, or all of them. Press **T** to switch the
  target between WIN11 (onboarded) and WIN11B (stock AV only).
- **Menu 6** is Sentinel and the hunting pack, and **7** is the CIS benchmark matrix.

### Step 6: Tear down

Menu **1 → 5 (Destroy)**. It lists what will be deleted and you type the resource group name to confirm. The kit polls
until the resource group is gone. Check the Azure portal afterward to confirm nothing
is still billing.

> Before you leave a lab idle, use menu **1 → 3 (Stop)** to deallocate compute, or set
> auto-shutdown from menu 1. The run transcripts in `logs\` beside the script
> (menu **1 → 8**) are the first place to look when something fails.

## Why a framework? (manual vs. automated)

Standing up this range by hand (5 VMs, networking, and every Defender and CIS
setting) is roughly **300 Azure portal clicks, 15 to 20 RDP/SSH sessions, 100+
typed commands, and 4 to 6 hours**, and a rebuild means doing it all again.

| Phase | By hand (portal + RDP) | ~Time | Framework |
|-------|------------------------|-------|-----------|
| RG + VNet + subnet + NSG | ~40 clicks | 20–30 min | menu 1 → 1 |
| 5 VMs (7-tab wizard each; Kali needs Marketplace terms) | ~180 clicks | 60–90 min | menu 1 → 1 |
| Promote the DC + seed users/SPNs | RDP + ~25 steps | 30 min | menu 2 → 1 |
| Join the victims to the domain | RDP each, ~10 steps | 30 min | menu 2 → 2 |
| Defender for Endpoint + CFA + network protection | portal + ~40 commands | 40 min | automatic + menu 4 |
| Sentinel workspace + enable + connectors | ~25 clicks | 20 min | menu 6 → 1 |
| CIS GPO import + OU + link | ~40 steps | 60 min | menu 7 |

**With the framework:** about 12 to 15 menu picks, each echoing its own
command. Deploy runs unattended, config steps are one pick each, and the whole
thing is reproducible and logged. A rebuild is one *Deploy* and one *Destroy*.

> **Teaching value:** every step prints the exact command it runs, so attendees
> still see the real `az`, `Set-MpPreference`, `Import-GPO` and Sentinel steps.
> The framework removes the typing and memorizing, not the learning.

## What it stands up

| VM | Image | Role |
|----|-------|------|
| **DC01** | Windows Server 2025 | `lab.local` domain controller; seeds the lab users and the Kerberoast/AS-REP targets |
| **WIN11** | Windows 11 Enterprise | victim **A**, onboarded to Defender XDR (MDE P2 + MDI) |
| **WIN11B** | Windows 11 Enterprise | victim **B**, **stock Defender AV only, not onboarded** (the baseline twin) |
| **KALI** | Kali Linux (plain base image) | attacker box; nothing is auto-installed, you SSH in and set up your own tools |
| **SRV01** *(optional)* | Windows Server 2025 | second target / file server |

- One resource group (`rg-defxdr-lab`), one VNet (`192.168.57.0/24`). DC01 is
  `.10`, KALI `.5`, WIN11 `.20`, WIN11B `.21`, SRV01 `.30`.
- The NSG only lets RDP/SSH in from **your public IP** (detected at deploy;
  re-lock it with menu **1 → 9** when you change networks).
- **Auto-shutdown is off by default** so a build isn't stopped halfway. Turn it
  on from menu **1 → 6** when you're done building.

### The defended-twin comparison
WIN11 and WIN11B are the same machine with one difference: WIN11 is onboarded to
Defender XDR and WIN11B runs only stock Defender AV. Run an attack against each
(menu **5 → T** toggles the target) and show the contrast: WIN11 lights up the
incident queue, while on WIN11B the AV may act locally but **nothing reaches the
XDR console**.

### A second, isolated copy
Menu **1 → D** builds an identical second lab in `rg-defxdr-lab-2` (its own VNet,
NSG, public IPs and AD forest, never peered to the first), and **2 → B** finishes
it. **C** switches which copy every menu acts on. **1 → X** destroys only the
second copy.

## How it drives the VMs

All in-guest configuration is pushed from your Windows box through
`az vm run-command`, so **no RDP/SSH is needed for setup**. The kit prints each
command before it runs it, so the room can follow along.

### CIS benchmark: prove what hardening stops (menu 7)
The same attack, run four ways:

| Cell | Posture | Box |
|------|---------|-----|
| 1 | **No XDR** (stock AV, no CIS) | WIN11B |
| 2 | **XDR** (onboarded, no CIS) | WIN11 |
| 3 | **XDR + CIS L1** | WIN11 |
| 4 | **CIS L1 only, no XDR** | WIN11B |

**You supply the CIS GPO zips.** Nothing from CIS ships in this repo. Export the
GPO backups with your own CIS SecureSuite membership, then point menu **7 → 6**
at them. Menu **7 → 8** splits CIS L1 into 14 per-area GPOs per policy
(`tools/Split-CisGpo.ps1`) and imports all 42 on DC01 **unlinked**, so you link
only what you want to demo. Menu **7 → 5** runs the whole matrix for one technique.

### Hunting
Menu **4 → H** runs the course hunts, and **4 → K** batch-runs the `queries\`
folder (`Invoke-KqlHunt.ps1`) against Defender XDR advanced hunting or Sentinel,
with CSV/JSON export and a PASS/EMPTY/FAIL test mode. See `Query-Guide.md` and
`Sentinel-Hunting-Pack.md`.

### Run logs
Every session is written to a timestamped transcript in `logs\` beside the
script, with `[CMD] / [STEP] / [RESULT] / [ERROR]` markers. Menu **1 → 8** tails
it, lists logs, opens the folder, or zips the latest one for sharing.

## Run it

```powershell
# interactive menu (the workshop way)
./DefXDRLabKit.ps1

# headless single steps
./DefXDRLabKit.ps1 -Action Deploy
./DefXDRLabKit.ps1 -Action ConfigureDC
./DefXDRLabKit.ps1 -Action BootDiag
./DefXDRLabKit.ps1 -Action Invoke -TechniqueId T-04
./DefXDRLabKit.ps1 -Lab 2 -Action Status      # act on the second copy
./DefXDRLabKit.ps1 -Action Stop
```

## Cost & safety

- **Stop (deallocate) or Destroy when idle.** Both are one menu pick.
- The kit only deploys after you **type the subscription name** to confirm it's
  your lab subscription, never a production or customer one.
- Inbound access stays locked to your IP. Keep any C2 listener on the lab-internal
  network so nothing leaves the range.
- Keep Defender running on the targets: generating telemetry for it to catch is
  the whole point.
